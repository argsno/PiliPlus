# AGENTS

## Local Android release build

CI runs `lib/scripts/patch.ps1 android` before `flutter build apk`; the patches change the Flutter SDK and the `material_ui` package, so a plain checkout does not compile (`textPainter` and friends are missing).

1. Apply the android patch set to the Flutter SDK (`FLUTTER_ROOT` from `android/local.properties`): `git reset --hard HEAD`, then `git apply` every patch from `lib/scripts/*.patch` in the order used by `patch.ps1` (common list, then `bottom_sheet_android`, `scroll_view`, `navigator`). Skip the iOS-only `bottom_sheet_ios_piliplus` / `geetest_ios` patches.
2. Apply `lib/scripts/material/*.patch` inside the `material_ui-<version>` directory in the pub cache; all nine apply to `material_ui 1.11.0`.
3. Revert both afterwards (`git reset --hard` in the SDK, `git apply -R` in the pub cache), otherwise other projects on the same Flutter version inherit PiliPlus behaviour.

Build command (JDK 21, arm64 only):

```sh
flutter build apk --release --target-platform android-arm64 --split-per-abi \
  --build-name=2.2.1-<short hash> --build-number=$(git rev-list --count HEAD) \
  --dart-define-from-file=pili_release.json --no-pub
```

Notes:

- `android/app/build.gradle.kts` uses `android/key.properties` when present and falls back to the debug signing config, so without the keystore the "release" APK is debug-signed.
- `compileSdk`/`targetSdk` are 37. The SDK manager installs that platform as `platforms/android-37.0`, but AGP 9.1 resolves `android-37`; a local `android-37 -> android-37.0` symlink in `$ANDROID_HOME/platforms` is required unless the SDK ships the unversioned directory.
- `pili_release.json` is generated by `lib/scripts/build.ps1` in CI and is gitignored; it must exist for `--dart-define-from-file`. `pubspec.yaml` keeps the plain `2.2.1+1` version, so pass `--build-name`/`--build-number` instead of editing it.

## Local macOS release build

Use the `patch.ps1 macOS` platform set: the same common `lib/scripts/*.patch` list, but skip `bottom_sheet_android`, `scroll_view` and `navigator`; apply the eight common `lib/scripts/material/*.patch` files and skip `bottom_sheet_android`.

```sh
flutter build macos --release --build-name=2.2.1 \
  --build-number=$(git rev-list --count HEAD) \
  --dart-define-from-file=pili_release.json --no-pub
```

Notes:

- Run `flutter pub get` once before `flutter build macos`. It is what makes the tool insert the CocoaPods `#include? "Pods/Target Support Files/Pods-Runner/Pods-Runner.<config>.xcconfig"` lines into `macos/Flutter/Flutter-{Debug,Release}.xcconfig`; with `--no-pub` on a checkout that lacks those lines the build fails with `Unable to load contents of file list: '/Target Support Files/...'` because `PODS_ROOT` never resolves. `pub get` leaves an already patched `material_ui` untouched.
- The first build may migrate the Xcode project (deployment target 12.0, Podfile platform, scheme) and rewrite `macos/Podfile.lock`; `git checkout -- macos/` afterwards if those changes are not wanted.
- Use the plain `2.2.1` build name for macOS (as CI does): characters other than digits and dots are stripped from `CFBundleShortVersionString`, so `2.2.1-<hash>` becomes `2.2.1217545`.
- `create-dmg` is not installed locally; `hdiutil create -volname PiliPlus -srcfolder <dir with PiliPlus.app + /Applications symlink> -ov -format UDZO out.dmg` is enough. The app is ad-hoc signed (`CODE_SIGN_IDENTITY = "-"`), so Gatekeeper only lets it open via right-click or `xattr -d com.apple.quarantine`.
